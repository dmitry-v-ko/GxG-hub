## Should fix

1. **SC-09 looks for the caller's text only on the success path** (`tools/gxg-connector-check/src/gxg_connector_check/checks.py:331-336`)
   - **What this is:** SC-09 proves that the caller's free text (a query, a message) never reaches a log line. It
     sends a unique marker in every free-text field and searches the logs for it.
   - **Problem:** The marker is sent only after `running.fail(None)`, so only successful calls carry it. The loop
     over the failure modes above it uses `call.args` (`query: "status"`), which the check never looks for. Case:
     demo's `notes_search` wrapped in `except GxgError: logs.audit.warning("search failed for query %s", query)`
     -> `check-connectors` green (all checks). The same wrapper that also logs the provider token turns SC-09 red,
     so the error path does run and is captured; only the text is not looked for. "Log the query when the search
     fails" is the most common way a text reaches a log.
   - **Fix:** use the marker in the failure-mode loop as well: send `{**call.args, prop: marker}` there (one more
     inner loop over the free-text properties, or put the marker into the args before that loop).
   - **If we skip it:** a KB or Telegram service that logs the search text or message on a provider error passes
     the suite (SEC-18).

2. **The cursor check uses a principal of another tenant only** (`checks.py:150-161`, `pages`)
   - **What this is:** the demo spec says the cursor is "signed by the connector, bound to the principal and the
     query" (`docs/specs/demo-connector-v1.md:66`); the check claims "the cursor is bound to its caller".
   - **Problem:** the only foreign caller is `harness.stranger` (another tenant). Cases: demo with the cursor bound
     to `[tenant, query, boards, limit]` (no principal) -> all green; demo with the cursor bound to
     `[tenant, principal, boards, limit]` (no query) -> all green.
   - **Fix:** also use the cursor as `harness.nobody` (same tenant) and with another `query` (a changed free-text
     argument); both must be `invalid_input`.
   - **If we skip it:** low harm today (results are filtered again for the caller), but the spec rule is not
     guarded.

3. **A hidden resource named together with a readable one is not checked** (`checks.py:296-310`, SC-05)
   - **What this is:** GR-17: a resource the caller named and may not read -> `not_found`, never a quietly smaller
     result.
   - **Problem:** SC-05 names the hidden board alone. Case: demo that raises `not_found` only when none of
     `board_ids` is readable and otherwise drops the unreadable ones -> all green; `board_ids: ["a-public",
     "a-secret"]` returns the a-public notes as if a-secret were empty.
   - **Fix:** in SC-05 also call with `hidden` plus one readable resource of `call.args` (e.g. merge the readable
     id into the `*_ids` list) and expect the same `not_found`.
   - **If we skip it:** the agent cannot tell "no data" from "no access" (the reason of GR-17).

4. **`tests/ci/test_mutmut_sh.py` deletes the real `mutants/` of `tools/gxg-connector-check`** (`tests/ci/test_mutmut_sh.py:36-40`, `scripts/ci/mutmut.sh:37-38`)
   - **What this is:** the test runs the real `scripts/ci/mutmut.sh` with a stub `uv`.
   - **Problem:** the script `cd`s into `tools/gxg-connector-check` of the repository and runs `rm -rf mutants`, and
     the stub writes `mutants/mutmut-cicd-stats.json` there. Every `uv run pytest` wipes the results of an earlier
     mutmut run of that package; a `mutmut.sh` running in another terminal (40 minutes) loses its directory midway.
     In `check-all.sh` the order (pytest before mutmut) hides it.
   - **Fix:** run the script from a copy: copy `scripts/ci/mutmut.sh` and `mutmut-equivalent.txt` into
     `tmp_path/scripts/ci/`, create `tmp_path/tools/gxg-connector-check/`, run the copy.
   - **If we skip it:** lost mutmut results and a confusing red mutmut run for whoever runs both.

5. **The copier update test is red on a detached checkout** (`tests/toolkit/test_template.py:152-180`)
   - **What this is:** the e2e test clones the repository, commits a template change on the clone's HEAD and runs
     `copier.run_update(vcs_ref=new)`.
   - **Problem:** when the repository under test is checked out detached (a `git worktree add --detach <sha>`, a
     CI checkout of a commit), the clone is detached too; the new commit is on no branch, copier's own clone does
     not fetch it, and the test fails: `git worktree add ... 312006d…: invalid reference`. Seen in this review on
     a worktree of 5cca255; on the branch it passes.
   - **Fix:** `git -C hub switch -c template-change` before the commit (one line).
   - **If we skip it:** the gate is red whenever someone checks a commit rather than a branch.

## Nice to have

6. **The documented `copier update` leaves the kit pin behind** (`templates/python-fastmcp/README.md:3`, `copier.yml:13`)
   - **What this is:** the README says a service follows the template with
     `uvx copier update --vcs-ref <commit> --data kit_rev=<commit>`, then `uv lock`.
   - **Problem:** `pyproject.toml` is in `_skip_if_exists`, so the update never rewrites it. Run here: generated at
     5cca255, updated to a new hub commit -> `server.py` and `.copier-answers.yml` (`kit_rev`) move, but both
     `rev = "5cca255…"` in `pyproject.toml` stay; `uv lock` changes nothing. The service runs new template code on
     the old kit and the old conformance suite while its answers file claims the new one.
   - **Fix:** one more README step ("bump `rev` of both git dependencies in `pyproject.toml`"), or a test assertion
     that names the stale pin.
   - **If we skip it:** new checks of the suite silently do not reach services that "followed" the template.

   - **Fix:** backlog: reconcile needs the tenant (from the Approval Service record or the request) to check it.
   - **If we skip it:** nothing in v1.
