## Findings

### Must fix

### Should fix

1. **Путь W: webhook проверяет tenant и подписывает JWS только для `tools/call`. Вывод ADR «JWS обязателен на коннекторе для всех методов» с этим несовместим** (`spikes/m4.1-gateways/toolhive/webhook.py:46-47`; `docs/adr/0002-gateway-choice.md:92` п.2 (3) и (5); `reports/conformance/M4.1.json` `path_w_threats[2]`)
   - **What this is:** п.2 (3) ADR пишет, что при прямом обращении к прокси «tenant проверит webhook». п.2 (5) и `path_w_threats` делают вывод, что обход webhook безопасен, потому что коннектор требует JWS «для всех методов, не только для `tools/call`».
   - **Problem:** Для всех методов, кроме `tools/call`, webhook отвечает `allowed` без проверки tenant и без JWS. Проверил вживую: агент t-beta со своим токеном IdP напрямую на прокси t-alpha получил `tools/list` коннектора t-alpha (200, дошло до echo без JWS). Так же пройдут `resources/read` и `prompts/get`, если коннектор их отдаёт.
     - Если выполнить вывод ADR буквально и требовать JWS на всех методах, коннектор начнёт отказывать в `initialize` и `tools/list` всем легитимным агентам: webhook для этих методов JWS не подписывает.
     - Если не выполнять, методы кроме `tools/call` на пути W идут без tenant-проверки.
     - Ни один из двух вариантов в стоимости не учтён. Подпись всех методов означает JWS без `tool`/`ahs`, то есть ещё одну правку SEC-03 сверх канала `_meta`.
     - В ContextForge + C коннектор тоже отдаёт `tools/list` без identity, но до коннектора может дойти только ContextForge (SEC-04). На пути W прокси открыт агентам, пока не закрыта сеть.
   - **Fix:** В п.2 (3) и (5), `path_w_threats` и п.9 записать, что webhook стенда закрывает tenant только на `tools/call`. Для остальных методов выбрать одно и добавить в стоимость: tenant-проверка в webhook для всех методов, или `--authz-config` / сеть как обязательная мера, или JWS для всех методов с правкой SEC-03. Не меняет рекомендацию. Это неполнота запасного варианта, а не ложь о проверенном: вызовы, о которых идёт речь в п.2 (3), действительно получают 403. → **minor**.

2. **Меры против переиспользования Bearer не закрывают повторную подпись через собственный прокси, а это бьёт по AS-08** (`docs/adr/0002-gateway-choice.md:92` п.2 (2); `M4.1.json` `path_w_threats[0]`)
   - **Problem:** ADR сам пишет: «С exchange-токеном он вызовет свой прокси, и webhook подпишет ему свежий JWS от имени агента». Перечисленные меры этого не закрывают:
     - `aud` = прокси плюс `--oidc-audience` оставляют exchange-токен годным именно для своего прокси;
     - сеть сформулирована как «коннектор не видит vMCP и **чужие** прокси», а свой прокси он видит;
     - остаётся только strip-auth, а его совместимость с `token_exchange` не проверена.
   - **Конкретный случай:** скомпрометированный коннектор t-alpha получил exchange-токен hermes (на стенде срок 3600 с). Он отправляет на свой прокси `tools/call` с любым tool и любыми аргументами и получает валидный JWS `sub=agent:t-alpha:hermes`, `tool`/`ahs` своего выбора. Этот JWS он передаёт как `requester.assertion` в Approval Service, и проверка AS-08 «MUST независимо проверить assertion» проходит. В ContextForge + C assertion привязана к реальному вызову агента: коннектор может только повторить её для того же `ahs`, а повтор ловит `jti`.
   - **Fix:** В п.2 (2) и `path_w_threats` добавить: сеть, где коннектор не может открыть соединение к своему прокси (только прокси → коннектор), либо strip-auth (проверить), либо короткий срок exchange-токена. И отметить последствие для AS-08. Запасной вариант, рекомендацию не меняет → **minor**. Origin: `missed_earlier`. Критик цикла 2 назвал этот путь, но в списке мер сам привёл те же неполные меры, и исполнитель их перенёс.

3. **ContextForge = 0 дней, хотя часть работы, которую для ToolHive считают переходом, у ContextForge стоит в M5** (`docs/adr/0002-gateway-choice.md:133,134,138,140`; `docs/implementation-plan-v1.md` M5 «Делаем»)
   - **Problem:** В M5 для ContextForge запланированы «правила `unified_pdp`» и «сетевая изоляция `demo`». ToolHive по п.9 платит за генерацию Cedar (входит в 3,5–5 дня) и NetworkPolicy (входит в 5–8 дней). Эквивалент этой работы на ContextForge ещё не сделан, но в ADR стоит 0 («вариант C сделан и проверен в M4»). Так что разница завышена в пользу ContextForge, грубо на 1–3 дня. Рекомендацию это не меняет: даже за вычетом ToolHive дороже на ≥ 7 дней плюс топология. Но владелец видит «0 против 12–17», а это не разница на одной базе.
   - **Fix:** Одна фраза у п.9: «0 — без M5; `unified_pdp` и сетевая изоляция есть в обоих вариантах, у ToolHive их заменяют Cedar и NetworkPolicy». → **minor**, `missed_earlier` (было с цикла 1).

4. **Статус п.4 для ContextForge расходится между ADR и отчётом** (`docs/adr/0002-gateway-choice.md:69` «частично»; `reports/conformance/M4.1.json` `matrix[3].contextforge.status = "not_run"`)
   - **Problem:** Статус `частично` не входит в список статусов ADR (`passed/failed/n/a/not_run`). В ADR стоит «частично», в отчёте — `not_run`. Из-за этого строка ContextForge в таблице выглядит лучше, чем доказано. Это пункт, где ToolHive выигрывает.
   - **Fix:** `not_run` (скрытые tools не проверялись, `unified_pdp` — M5) в обоих местах. → **minor**, `missed_earlier`.

- `run_midsession` переиспользует `call()` и `spike.call_tool("rpc", …)` с заголовками сессии, а для остановки берёт штатный `docker stop`. Своего MCP-клиента нет.
- `verify_tx.py` изменён на 3 строки: хранилище по ключу `(path, jti)`, PyJWT `PyJWKClient`.
- `--authz-config`, `--oidc-audience` и оператор — штатные возможности `thv`. Записаны, но не запускались, и это честно отмечено.
- Новых самописных компонентов нет. Повторно проверены `webhook.py`: альтернативы — плагин `gxg_identity` (это хук ContextForge, не сервис) и embedded auth server ToolHive (JWS ADR-0001 не выпускает). Своя реализация оправдана.

## Честность сравнения и рекомендация

- Сравнение не пострадало. Цикл 3 только ухудшил ToolHive, и обоснованно: docker socket = root на хосте, это проверено критиком цикла 2. Рекомендация «оставить ContextForge + C; ToolHive — запасной, production-топология не проверена; Docker MCP Gateway отклонить» следует из доказательств.
  - ContextForge проверен на всех путях M4.
  - У ToolHive путь W проверен механизмом на стенде с полным docker socket, а топология не проверена.
  - Docker MCP Gateway не даёт identity вызывающего и не умеет менять запрос, это проверено вживую.
- Перекосы в пользу ContextForge есть (находки 3 и 4), но они мелкие и вывод не переворачивают.
- У владельца есть всё нужное для решения: цена в днях по топологиям, условия пересмотра (M5, GO/NO-GO, условие 4), список непроверенного, модель угроз пути W.
