## Findings

### Should fix

1. **Путь C на ToolHive вне Kubernetes требует docker socket в каждом прокси, а стоимость и риски этого не учитывают** (`docs/adr/0002-gateway-choice.md:11,134,136`; `toolhive/run.sh:19`)
   - **What this is:** Путь W — это прокси `thv run` (или proxyrunner в Kubernetes) перед каждым коннектором. ADR считает топологию за 1–2 дня: «штатные образы; proxyrunner или `thv run` на каждый коннектор».
   - **Problem:** `thv` без container runtime не стартует вообще: `docker run --rm ghcr.io/stacklok/toolhive:v0.67.0@… run --help` → `no container runtime available … requires a Docker-compatible container runtime … or Kubernetes` (проверено критиком). Хостинг не выбран, Kubernetes в целевой платформе нет (`docs/specs/target-platform-v1.md:113-120`). Значит, вне Kubernetes каждый прокси получает `/var/run/docker.sock`, то есть права root на хосте. Этот прокси принимает трафик от vMCP (а без сетевой изоляции — и от агентов напрямую), а у ToolHive 55 GHSA. Один RCE в прокси — захват хоста со всеми коннекторами и ключами. Второй вариант — поднять Kubernetes ради оператора — в стоимость тоже не входит. ADR упоминает socket только как деталь стенда (п.5).
   - **Fix:** В п.9 и п.2 разделить топологию на два варианта: (а) Kubernetes + оператор (`MCPServer` + `MCPWebhookConfig`) с оценкой стоимости кластера и его эксплуатации; (б) `thv run` + docker socket на прокси, с явным риском «root на хосте» и мерами (rootless/socket-proxy, отдельный хост) или с отказом от этого варианта. Пересчитать «~7–10 дней» и фразу «реальная альтернатива».
   - **If we skip it:** Владелец выберет ToolHive по цене ~7–10 дней, а на деле получит либо Kubernetes, либо прокси с доступом root на хосте перед каждым коннектором.

2. **Прокси `thv run` передаёт коннектору Bearer-токен вызывающего; ADR об этом молчит** (`docs/adr/0002-gateway-choice.md:92`; evidence `webhook-c/echo-received.jsonl`)
   - **What this is:** В п.2 (2) ADR перечисляет, что прокси пропускает к коннектору заголовки клиента (`X-Forwarded-User-*`, `X-GxG-Identity`).
   - **Problem:** Пропускается и `Authorization`. В сыром логе echo стенда `webhook-c` (повторено): на пути `thv-proxy:direct` коннектор получает собственный токен агента с `aud: vmcp` и сроком 3600 с, на пути через vMCP — exchange-токен (без `aud`, 3600 с). `strip-auth` в `v0.67.0` включается только с embedded auth server (`TH/pkg/runner/middleware.go#L495-L527`), с `--oidc-issuer` — нет. Скомпрометированный коннектор с токеном агента (`aud: vmcp`) может вызвать через vMCP любой tool, разрешённый этому агенту, в том числе на других коннекторах tenant'а. С exchange-токеном он может вызывать свой прокси, и webhook подпишет ему свежий JWS от имени агента. В ContextForge+C коннектор токен агента не получает.
   - **Fix:** Добавить это в п.2 (2), п.5 и модель угроз. Меры: `aud` при exchange плюс `--oidc-audience` на прокси (токен годен только для своего прокси) и сетевая изоляция прокси; или embedded auth server с `disableUpstreamTokenInjection`, если он совместим с путём W. Проверить вживую не обязательно, достаточно записать.
   - **If we skip it:** Модель угроз пути W неполна: коннектор, которому по SEC-03 доверяют только identity из JWS, получает переиспользуемые учётные данные агента.

3. **`verify_tx.py` моделирует одно хранилище `jti` на два коннектора, поэтому «повтор на другой коннектор отклонён» — артефакт** (`toolhive/verify_tx.py:62-65`; `docs/adr/0002-gateway-choice.md:86`)
   - **What this is:** Скрипт отвечает на вопрос, закрыло бы хранилище `jti` коннектора повторы `token_exchange`-токена.
   - **Problem:** `seen` одно на все строки, и `/mcp/t-alpha`, и `/mcp/t-beta`. По SEC-03 хранилище общее для реплик **одного** коннектора (`docs/specs/security-v1.md:41`). Повтор токена с t-alpha на коннектор t-beta этот `jti` не встречал и прошёл бы. Скрипт пишет `replay_other_connector: true`, а ADR (п.2, критерии 2–3) — «отклоняет все 5 прямых повторов». Строкой ниже ADR сам пишет, что повтор на другой коннектор проходит из-за отсутствия `aud`. Два утверждения противоречат друг другу.
   - **Fix:** Ключ хранилища — `(path, jti)`: `seen` по `x["path"]`. В ADR: «отклоняет 4 из 5; повтор на другой коннектор закрывает только `aud`».
   - **If we skip it:** Читатель решит, что хранилище `jti` закрывает повтор на другой коннектор без `aud` у IdP. Это неверно.

4. **Fail closed пути W проверен только для webhook, мёртвого с самого старта** (`docs/adr/0002-gateway-choice.md:68,104`; evidence `webhook-c-down/observations.jsonl`)
   - **What this is:** ADR: «webhook недоступен — вызов не уходит».
   - **Problem:** В повторённом прогоне все 8 отказов происходят ещё до `tools/call`: на прямом пути падает `initialize` (`init_error … Webhook error`, 500), через vMCP backend не инициализируется (`tool not found`). Случай «webhook умер после того, как vMCP установил сессию с прокси» не выполнялся. По коду (`TH/pkg/webhook/mutating/middleware.go#L83-L131`) webhook зовётся на каждый разобранный запрос, а ошибка при `fail` даёт 500, так что отказ, скорее всего, есть, но это вывод по коду.
   - **Fix:** Шаг `docker stop m41-webhook` между `calls` и повторным `calls` в варианте `webhook-c-down` (одна-две строки в `run.sh`) или пометка «вызов посреди сессии — по коду» в п.3.
   - **If we skip it:** Самый вероятный в эксплуатации отказ (webhook упал под нагрузкой) не подтверждён, хотя ADR пишет `passed`.

5. **Против обхода Cedar прямым вызовом прокси ADR даёт два средства и пропускает третье, штатное** (`docs/adr/0002-gateway-choice.md:92` п.(3))
   - **What this is:** Агент со своим токеном IdP вызывает прокси мимо vMCP. Это проверено вживую (`thv-proxy:direct` принят). Webhook проверяет tenant, но не tool, поэтому скрытый tool того же коннектора тоже вызывается.
   - **Problem:** ADR: «нужно одно из двух: NetworkPolicy или `aud` у IdP». У `thv run` есть свой Cedar: `--authz-config` (`TH/cmd/thv/app/run_flags.go#L237`). Он стоит в цепочке после mutating webhook и до backend (`TH/pkg/runner/middleware.go#L202-L242`), то есть закрывает и скрытые tools на прокси. Это меняет и стоимость (политики генерируются дважды), и риск.
   - **Fix:** Добавить `--authz-config` на прокси как третий вариант (или как обязательный вместе с сетью) в п.2 и п.9.
   - **If we skip it:** Сравнение неполно в мелочи: у владельца нет самого дешёвого средства.

6. **Advisories, которые прямо касаются пути W, не связаны с ним** (`docs/adr/0002-gateway-choice.md:32,72,92` п.(5))
   - **What this is:** Путь W опирается на middleware mutating webhook.
   - **Problem:** Среди 55 GHSA есть обходы самого webhook-middleware за последние два месяца: GHSA-g7gq-2r4g-3qw8 (High, 2026-10-07: webhook и rate limit обходятся POST с не-JSON `Content-Type`) и GHSA-wj8g-gmv2-mpmv (2026-11-04: BOM в начале тела — fail-open webhooks пропускают запрос). ADR называет wj8g только в общем списке, g7gq не называет вовсе, а в п.2 (5) пишет лишь «молодой контракт». Для пути W обход webhook означает, что запрос доходит до коннектора без JWS. Коннектор его отклонит (`missing`), то есть fail closed сохраняется, но только пока коннектор требует JWS на каждом методе.
   - **Fix:** Одна фраза в п.2 (5)/п.7 с этими двумя GHSA и выводом «обход webhook = вызов без JWS, коннектор отклоняет; поэтому JWS обязателен на коннекторе для всех методов».
   - **If we skip it:** Неочевидно, что безопасность пути W держится на коннекторе, а не на webhook.

Lean-находок нет: `webhook.py` (~100 строк) переиспользует `verify_jws.canonical`, claims плагина `gxg_identity` встроены в ContextForge-хук и не вынимаются как функция; `interceptors.sh` и `sed`-варианты убрали дубли цикла 1.
