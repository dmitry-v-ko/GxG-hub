# M6 — стоп-эскалация: оценка ограничена 5 до доступа к серверу KB (`kb_access`)

**Статус:** стоп по «Лимитам и эскалации» — 4 цикла улучшений исчерпаны, оценка не растёт (5.0 четыре раза), а ограничение снимается только доступом, который даёт владелец. Всё, что можно сделать без доступа, сделано; последняя находка критика (N1) исправлена после последнего цикла и ждёт финального независимого критика.

## Что нужно от владельца

Gap-аудит сделан (тред M11 по клону `dmitry-v-ko/gxg_agents_v2@f1c4d6d`, `docs/audits/kb-gap-audit.md`). Главное: **кода сервера KB MCP (`kb_access`) в `gxg_agents_v2` нет, базовой схемы `kb.*` в миграциях нет** (G1, G2). Поэтому AC-M6-04 и проверку AC-M6-03 для сервера KB выполнить нельзя.

Нужно одно из двух:

1. **Read-доступ к репозиторию `kb_access`** (где он — вопрос Q7) **и DDL схемы `kb` без данных** (`pg_dump --schema-only --schema=kb` + `public.kb_*`, G2) — тогда поднимаем локальную копию KB, гоняем тесты адаптера и стенда против неё и тест AC-M6-04 по процедуре аудита.
2. **Или тестовый инстанс `kb_access`** с включённой auth и синтетическими read- и write-ключами (без живых данных).

Плюс для продовой connection — какой upstream за `kb.agents.gxg-labs.com/mcp` (Q5).

Ещё: эта сессия не может сама подключить репозиторий — `add_repo` для `gxg_agents_v2` дважды отклонён политикой разрешений сессии (auto mode). Аудит поэтому делал тред M11.

## Решения по умолчанию (действуют)

Q1–Q4, Q6 — варианты аудита по решению оркестратора от имени владельца: коллекция = `entity_type.key`; одна connection на tenant; читателям только `published`; write-tools скрыты от read-ключа (wrapper проверяет в `/readyz`); копии миграций только для тестов. Новые вопросы: **Q8** — фильтр `status` в `kb_search` (иначе `complete: false` даёт один бит о скрытых черновиках).
