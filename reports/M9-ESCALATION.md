## 1. Компрометация `ui` может подделать решение человека (вопрос из закрытия M7)

**Вариант по умолчанию (сделан).** Матрица AS-27 плюс сужение, которое спеку не меняет:

| Что | Где |
| --- | --- |
| `gxg_ui` пишет только через `gxg_decide`, `gxg_resolve_manual`, `gxg_link_code` и таблицу passkey; `INSERT outbox` и прямая запись `approver_links` отозваны | `0002_ui_notifier.py`, `test_roles.py` |
| Набор approver'ов tenant'а (роль `approver` по bundle ∩ `approvers` политики) замораживается при T1 в `allowed_approvers`; `gxg_decide` отказывает всем вне набора (NULL = никто) | `intents.approver_set`, `0001_core.py` |
| В БД: requester ≠ approver, `oidc:`-principal, tenant (через набор), статус и `version`, `args_hash`, срок, один голос на человека, кворум по числу разных людей | `gxg_decide` |
| T18 — только `oidc:`-principal | `gxg_resolve_manual` |

**Что остаётся открытым при компрометации `ui`** (злоумышленник выполняет код процесса `ui` или владеет его
DSN, ключом сессий или preview-ключами):

| Путь | Почему не закрыт |
| --- | --- |
| Решение от имени **любого настоящего approver'а** этого intent'а | Человека аутентифицирует сам `ui` (OIDC, сессия). БД видит только строку `p_approver` |
| Подделка step-up (`p_step_up = true`) | WebAuthn-assertion проверяет `ui`; БД получает булево значение. Таблица passkey пишется ролью `gxg_ui`: можно зарегистрировать свой ключ любому approver'у |
| Кворум 2 «двумя людьми» | Следует из первого пункта: два разных `p_approver` из набора |
| T18 от имени любого человека, в том числе без роли `tenant_admin` | Роль `tenant_admin` в БД не известна (только `oidc:`-префикс) |
| Чтение preview и канонических args всех tenant'ов, у которых ключ в `ui` | Это и есть назначение preview-ключа (AS-28) |
| Подмена ссылки в Telegram | Нет: бот (`notifier`) — отдельный процесс; `ui` больше не пишет `approver_links` и `outbox` |

Чего компрометация `ui` **не** даёт: исполнить эффект (нет прав на `executions`, нет ключа execution token), решить
intent чужого tenant'а или от имени человека вне замороженного набора, решить intent после срока, на другие args или
на устаревшую версию, отменить запись аудита.

**Предложение владельцу (спека не менялась).** Привязать решение к подписи человека, которую `ui` подделать не может:

1. WebAuthn-assertion на **каждое** решение (не только `high_risk`), challenge = `H(intent_id ‖ args_hash ‖ version ‖ decision)`.
2. Проверяет её не `ui`, а отдельный внутренний процесс `decider` (своя роль БД, без выхода наружу). Проверка в самой
   БД возможна только с расширением: passkey почти всегда ES256 (ECDSA P-256), а в pgcrypto её нет (pgsodium умеет
   Ed25519, но не P-256). Поэтому практичнее процесс. Только его роль получает `EXECUTE gxg_decide`; `ui` пересылает
   сырой assertion.
3. Регистрация passkey — не через `ui`, а через `decider` с подтверждением вне `ui` (например, одноразовая ссылка от
   оператора или повторный вход в IdP с `acr`/`max_age`), иначе скомпрометированный `ui` зарегистрирует свой ключ.
4. В `decisions` хранить assertion (authenticatorData, clientDataJSON, signature, credential_id) — решение становится
   проверяемым задним числом.

Цена: изменение AS-16 («step-up только для `step_up_required`») и AS-27 (новая роль, перенос `EXECUTE gxg_decide`),
новый процесс, passkey обязателен каждому approver'у. Альтернатива дешевле, но слабее: проверка ID token IdP в БД
(подписан IdP, но живёт минуты и не привязан к конкретному решению — повторяется скомпрометированным `ui`).

## 2. Набор approver'ов замораживается при T1

Approver, добавленный в bundle после T1, не может решить этот intent (до его срока, ≤ 24 ч). Удалённый — не может
(проверка текущего bundle в `ui`). Вариант по умолчанию — заморозка (AP-04: «позднее изменение политики не меняет
созданные intents»). Альтернатива: таблица ролей в БД, которую пишет `api` из bundle (новая таблица в AS-27).

## 3. Таблицы, которых нет в AS-27

- `link_codes` + `gxg_link_code` (ui) / `gxg_link_claim` (notifier). По AS-27 у `gxg_notifier` только
  `SELECT approver_links`, а запись связи «код → telegram_user_id» знает только бот. Вариант по умолчанию: запись через
  функцию `SECURITY DEFINER`, которую вызывает только `gxg_notifier`.
- `webauthn_credentials` (AS-17 требует зарегистрированных passkey). Пишет `gxg_ui` (INSERT, UPDATE `sign_count`).

Просьба: внести обе таблицы в матрицу AS-27 или выбрать другой механизм.

## 4. Канонические args в `preview_ciphertext`

EFF-33 и карточка AS требуют показать канонические args, а AS-27 не даёт `gxg_ui` читать `args_ciphertext`.
Вариант по умолчанию: `api` при T1 кладёт в preview-конверт `{preview, canonical_args}` (ключ preview); `ui` сверяет
хеш args с `canonical_args_hash` и не даёт одобрить при расхождении.

## 5. AC-M9-01 «затем `succeeded`» без executor'а

M8 (executor) не на базе M9. E2E доводит intent до `succeeded` переходами T7, T9, T11 через настоящие функции ролей
`gxg_executor` и `gxg_api` (тестовый драйвер, не прямой UPDATE). После мержа M8 — заменить драйвер настоящим executor'ом.
