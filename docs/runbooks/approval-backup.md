# Runbook: бэкап и восстановление Approval Service (M14, OPS-03, OPS-04, RET-04)

Скрипт — `scripts/ops/approval_backup.py`. Проверено на локальном PostgreSQL 16: `approval/tests_db/test_backup.py`, `tests/deploy/test_approval_backup.py`. Живой стенд не проверялся.

## Что и как хранится

- Дамп — `pg_dump --format=custom`, шифруется на лету (AES-256-GCM, куски по 16 MiB), на диск открытым текстом не попадает. Файл `gxg-approval-<UTC>.dump.enc`, права 0600.
- Ключ — 32 байта base64url в `GXG_BACKUP_KEY`. Хранить отдельно от бэкапов (менеджер секретов оператора). Без ключа бэкап не открыть.
- Срок — 35 дней (RET-04). Возраст берётся из имени файла, а не из mtime: скопированный файл не «молодеет». Файлы с другими именами скрипт не трогает.
- База — через переменные libpq (`PGHOST`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`). В argv секретов нет. Роль — владелец схемы (`gxg_owner`): ролям процессов читать всё нельзя (AS-27).
- Где запускать: хост оператора или задание с клиентом `pg_dump`/`pg_restore` той же major-версии, что сервер, и пакетом `gxg_approval` (`uv sync`). PITR самой базы настраивается у провайдера базы и этим скриптом не заменяется.

## Бэкап (раз в сутки)

```bash
export GXG_BACKUP_KEY=...   # из менеджера секретов
PGHOST=... PGUSER=gxg_owner PGDATABASE=approval PGPASSWORD=... \
  uv run python scripts/ops/approval_backup.py backup --dir /var/backups/gxg-approval
```

Команда пишет файл целиком (сначала `.part`, потом переименование) и удаляет бэкапы старше 35 дней. Если `pg_dump` упал, файл не создаётся, код выхода 1.

**Проверка срока хранения (AC-M14-02):** `approval_backup.py check --dir <каталог хранилища>`. Код 1 и строки `FAIL older than 35 days`, если есть старый бэкап. Запускать по расписанию и после каждой копии в удалённое хранилище; для удалённого хранилища — включить в нём правило удаления через 35 дней и сверять `check` на его локальной выгрузке.

## Восстановление на чистый стенд

Нужно при потере базы и для учений. Порядок важен: пока база не проверена, эффекты идти не должны.

1. **Остановить эффекты.** `gxg-approval switch set --scope global --reason "restore from backup"` (если старая база ещё отвечает) и остановить `executor`, `sweeper`, `api`, `mcp`, `ui`, `notifier`.
2. **Создать пустую базу** владельцем и применить роли: `createdb -O gxg_owner approval_restored`, затем `approval/deploy/roles.sql`; роли процессов должны иметь `LOGIN` (как при развёртывании).
3. **Восстановить:**
   ```bash
   export GXG_BACKUP_KEY=...
   PGHOST=... PGUSER=<суперпользователь или gxg_owner с правом SET ROLE> \
     uv run python scripts/ops/approval_backup.py restore --file gxg-approval-<UTC>.dump.enc --target approval_restored
   ```
   - Скрипт отказывается работать с непустой базой (есть таблица `intents`).
   - Объекты создаются от `gxg_owner`, права на функции и таблицы переносятся.
   - **Сразу после загрузки выполняется очистка RET-01** (`gxg_purge`, срок `GXG_RETENTION_DAYS`, по умолчанию 30): payload intents, терминальных дольше срока, не возвращается из старого бэкапа. Итог печатается: `restored: purged=N, <status>=<count>, ...`.
4. **Сверить состояния** с последним известным: счётчики по статусам в выводе скрипта, `SELECT status, count(*) FROM intents GROUP BY 1`, метрика `gxg_intents_outcome_unknown`.
5. **Запускать в таком порядке:** `api` → `sweeper` → `executor` последним. Kill switch снять только после шага 4: `gxg-approval switch clear` (нужен свежий вход в IdP, см. approval-ops §1).
6. **Что ждать от executor'а.** Терминальные intents (`succeeded`, `reconciled_*`, `failed`) он не трогает: повторных вызовов провайдера нет. `outcome_unknown` он сверяет через `reconcile`/`lookup`, а не повторной отправкой (AS-04). Единственные вызовы — для intents, которые на момент бэкапа были `approved` и не ушли к провайдеру. Если между бэкапом и аварией executor успел отправить сообщение, а бэкап этого не знает, intent выглядит неисполненным: перед шагом 5 сверить с провайдером все `approved`/`executing` intents (журнал отправки провайдера) и пометить такие вручную по approval-ops §4.
7. Записать восстановление в журнал инцидентов: какой бэкап, кто, результат сверки.

## Потеря или смена ключа

- Новый ключ — новым бэкапам. Старые открываются только старым ключом, держать его до истечения последнего бэкапа (≤ 35 дней).
- Потерян ключ — бэкапы потеряны; сразу сделать новый бэкап новым ключом.
- Ключ скомпрометирован — заменить ключ, затем удалить бэкапы, зашифрованные им, и сделать новый.
