# Opportunity Engine — текущая минимальная архитектура

> **Статус:** принятое рабочее направление после критического разбора (Ponytail / «сначала переиспользование»), 21 ноября 2026.  
> **Это:** продуктово-архитектурная концепция, **не** техническая спецификация внедрённой системы.  
> **Разделение областей:** Opportunity Engine — интеллект коммерческого роста; [GxG Hub](../intent.md) — инфраструктура управляемого доступа к инструментам. Этот документ не меняет scope, security-контракты или реализацию GxG Hub.  
> **Связанные документы:** [стратегия продукта](OPPORTUNITY_ENGINE_STRATEGY.md) · [исследование 39 open-source кандидатов](OPPORTUNITY_ENGINE_OPEN_SOURCE_DONORS_2026-11-21.md) (исследование — каталог доноров, **не утверждённый стек**).

## 1. Что мы строим

**Opportunity Engine** — агентно-совместимая система коммерческого мышления и экспериментирования для B2B-роста, а не универсальная AI-платформа. Система помогает находить возможности, формулировать обоснованные гипотезы, организовывать проверки существующими агентами, собирать результаты и корректировать последующие решения.

Цикл: **Discover → Activate → Experiment → Learn → Scale**.

Первая модель применения: собственные B2B-продажи и маркетинг solo founder; затем — AI-enabled service для клиентов. Предметная область — B2B, но базовый цикл ведения экспериментов не обязан быть привязан к маркетингу.

**Главная проверяемая гипотеза продукта:** доступ к структурированному контексту, методам и результатам прошлых экспериментов улучшает выбор следующего коммерческого действия по сравнению с обычным LLM или простым поиском по документам. Это пока не доказано.

## 2. Текущая логическая схема

\`\`\`text
                  OPPORTUNITY ENGINE
        цели → гипотезы → решения → выводы
                         │
      ┌──────────────────┼────────────────────┐
      │                  │                    │
 Company Context    Growth Knowledge    Experiment Memory
 что продаём,        frameworks,         гипотезы, план,
 кому и почему;      skills, методы,     evidence, метрики,
 ограничения         playbooks           outcomes, learnings
      └──────────────────┼────────────────────┘
                         │
             Task / Context Package
     нужная задача + минимальный контекст
      + ссылки на доказательства + ограничения
                         │
             AI-агенты (заменяемые)
       Hermes / Claude / другие агенты
                         │
                      GxG Hub
     MCP-доступ · права · политики · approvals*
                         │
       существующие сервисы и источники
 CRM · Signals · аналитика · SEO · контент · API
                         │
          структурированные результаты
                         │
         Evidence → Review → Learning
                         │
          выбор следующего эксперимента
\`\`\`

\`*\` В GxG Hub часть security/approval функций описана как целевая архитектура / PoC и **не должна трактоваться как уже production-готовая**.

**Принцип владения:** агенты исполняют; внешние источники остаются источниками данных; Opportunity Engine владеет предметными правилами выбора гипотез и связями результатов с ними. Ни агент, ни MCP gateway не являются единственным владельцем экспериментальной памяти.

## 3. Четыре наших рабочих компонента — без обязательных новых сервисов

### 3.1 Company Context

Структурированное представление коммерческой реальности компании: продукты, ICP, персоны, потребности, офферы, позиционирование, конкуренты, каналы, экономика, ресурсы, ограничения, ранее сделанные попытки. Разделять *факты*, *заявления*, *предположения* и *выводы*; указывать источник и дату актуальности.

**Что создаём сами:** минимальный словарь/онтологию и правила сборки контекста под задачу. **Что переиспользуем:** существующее хранилище документов/данных, шаблоны и retrieval. Новый backend не является обязательным.

### 3.2 Growth Knowledge

Организованные фреймворки, методологии, playbooks и agent skills с условиями применимости, входными данными, ограничениями и проверяемым output. Ценность — не количество текстовых навыков, а качественная навигация и применимость.

**Что создаём сами:** отбор, связи и адаптацию методов к собственным B2B-сценариям. **Что переиспользуем:** готовые открытые skills, без создания собственного агента.

### 3.3 Experiment Memory

Минимальный **стандарт записи**, а не обязательно собственная программа:
- гипотеза; для кого/в каком контексте; основания и предыдущие проверки;
- план теста, критерий успеха **до запуска**, границы, ответственный, разрешения;
- действия, ссылки на артефакты, измерения и исходные данные;
- исход, наблюдения, неопределённость и ограничения интерпретации;
- решение: остановить / изменить / повторить / масштабировать;
- вывод, условия применимости и связь с последующей гипотезой.

**Что создаём сами:** контракт записей, дисциплину их заполнения, правила сопоставления. **Что переиспользуем:** существующее структурированное хранилище, если оно покрывает API, связи и историю. Grist **не** является обязательным.

### 3.4 Opportunity Intelligence

Правила выбора следующего наиболее полезного эксперимента: релевантность задачам бизнеса, реалистичность исполнения, сигналы спроса, стоимость и скорость проверки, коммерческий потенциал, предыдущий опыт, доказательства и неизвестные факторы.

**Что создаём сами:** предметную логику и критерии качества рекомендаций; сперва это могут быть инструкции/skills и review человеком, а не новый AI-service. Не выдавать корреляцию или один удачный тест за причинный закон.

## 4. Протокол взаимодействия компонентов

1. Получить коммерческую цель и пределы полномочий.
2. Собрать **Context Package**: цель, scope компании, факты с источниками, подходящие методы, прошлые эксперименты, доступные инструменты, формат результата.
3. Агент формулирует гипотезу, критерии успеха и план. Человек подтверждает действия с последствиями.
4. Агент выполняет задачу через разрешённые инструменты. GxG Hub **только** обеспечивает контролируемый доступ, а не управляет всем growth-процессом.
5. Результаты и ссылки на первичные данные сохраняются в независимом хранилище; отделяем «действие выполнено» от «эффект доказан».
6. Проводим review: что наблюдалось, чему научились, чего не знаем, что делать далее.
7. Следующий агент получает **минимально достаточный** актуальный контекст, а не всю историю проекта.

## 5. Что НЕ строим по умолчанию

- собственный универсальный LLM/agent framework, многоагентный оркестратор и task-Kanban;
- ещё один MCP gateway, коннекторный фреймворк или универсальную библиотеку API;
- собственную векторную БД, graph engine, общий RAG/long-term memory engine;
- отдельную CRM, аналитическую платформу, A/B-engine, content scheduler;
- монолитный «GrowthOS», который дублирует готовые сервисы;
- Grist и Activepieces **не включаем в обязательный стек**: они становятся опциями только при выявленном конкретном пробеле.

Допускаются точечные изменения при доказанном отсутствии подходящего готового решения. Приоритет: **не делать → использовать существующее → настроить → интегрировать → написать минимальный код**. Безопасность и проверяемость не упрощать ради экономии кода.

## 6. Реально имеющиеся части и неизвестное

- **AI-исполнители:** пользователь уже работает с Hermes, Claude и другими агентными средами. Не закрепляемся за одной.
- **GxG Hub:** отдельный проект на базе [IBM ContextForge](https://github.com/IBM/mcp-context-forge), ориентированный на MCP, connector contracts и security. По [README GxG Hub](../README.md) текущий статус — каркас/PoC, не production.
- **Источники данных и собственная база знаний:** существуют/планируются в окружающей экосистеме, но их полнота, API и схемы **не аудированы в этом документе**.
- **Experiment system of record:** конкретный backend **не выбран**, и это намеренно. Сначала проверяем уже имеющееся хранилище.
- **Специализированные AI skills и процессы:** есть готовые доноры ниже; они **не признаны внедрёнными**, пока не пройдён реальный сценарий.

## 8. Ближайший проверочный сценарий и критерий добавления новых технологий

**Один end-to-end B2B-тест**, без добавления обязательной инфраструктуры:
1. Существующий Company Context → выбранная коммерческая возможность и формализованная гипотеза.
2. До действия фиксируются критерий успеха и допустимые затраты/доступы.
3. Один существующий агент через доступные инструменты выполняет исследование/создание материалов/ограниченное действие.
4. Сохраняются артефакты, фактические данные, ограничения и review.
5. Другой агент получает сокращённый Context Package и предлагает следующую гипотезу с ссылками на предыдущее evidence.

Новый сервис добавляем **только если** конкретный шаг нельзя надёжно выполнить существующим инструментом. Проверяем: API, machine-readable export, переносимость данных, secure multi-client boundaries, стоимость сопровождения и возможность замены провайдера.

## 9. Что это не утверждает

- Не утверждает, что система уже учится выбирать более прибыльные гипотезы.
- Не утверждает, что GxG Hub или доноры прошли production security audit.
- Не утверждает, что существующее хранилище уже подходит для всех Experiment/Evidence/Decision records.
- Не требует переноса конфиденциальных данных клиентов в общий контекст; отдельная изоляция и права обязательны.
- Не выбирает единственный универсальный «лучший» open-source проект до практической проверки.

**Формула:** мы строим **систему, которая решает, какой маркетинг имеет смысл делать, как это проверить и чему научиться**; исполнение, интеграции и общую память максимально переиспользуем.
