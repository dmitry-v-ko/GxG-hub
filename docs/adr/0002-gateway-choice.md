# ADR-0002: Выбор MCP-шлюза: ContextForge, ToolHive или Docker MCP Gateway

**Статус:** Accepted — ContextForge v1.1.1 + вариант C; ToolHive — запасной кандидат на случай провала условия 4 в M5; Docker MCP Gateway отклонён. Решение владельца 2026-11-21 ([журнал](../../reports/progress.md) ветки плана, коммит `3f4c736`). Спайк M4.1, 2026-11-21. Проверка условия 4 в M5 — раздел [«M5: условие 4»](#m5-условие-4).
**Связано:** [ADR-0001](0001-identity-propagation.md) (вариант C на ContextForge, Accepted), [SEC-03, SEC-04](../specs/security-v1.md#identity), [Roadmap → GO/NO-GO](../specs/roadmap-v1.md#go--no-go). Стенды: [`spikes/m4.1-gateways/`](../../spikes/m4.1-gateways/README.md).

## Рекомендация

**Оставить ContextForge с вариантом C.** ToolHive держать запасным кандидатом, Docker MCP Gateway отклонить.

- **ContextForge** — identity доходит до коннектора, все атаки M4 и fail closed проверены, переход ничего не стоит: работа M4 уже сделана. После цикла 2 это уже не «единственный» вариант, а самый дешёвый: ToolHive проходит те же атаки, но стоит ~12–17 дней плюс эксплуатацию Kubernetes (или ~9–12 дней с прокси, которым нужен docker socket, то есть root на хосте) и правку SEC-03.
- **ToolHive vMCP** изолирует tenant'ов лучше ContextForge: Cedar с deny by default, фильтрация `tools/list` по политике, скрытый tool нельзя вызвать по имени. Всё это проверено на стенде. Но multi-tenant модели у него нет: tenant — это claim IdP плюс политики, которые мы пишем сами. Своего механизма identity для коннектора у ToolHive тоже нет. Ближе всего `token_exchange` (RFC 8693): токен подписан IdP, `jti` новый на каждый вызов, но привязки к tool и аргументам нет. Вариант C на ToolHive **возможен без форка и без своей сборки**: mutating webhook прокси `thv run`/proxyrunner за vMCP подписывает JWS формата ADR-0001 и кладёт его в `params._meta`. Это проверено на стенде: все вызовы агентов приняты коннектором с верной identity, все 7 прямых атак M4 отклонены с ожидаемой причиной. Цена — JWS в `_meta`, а не в заголовке (правка SEC-03 и `IdentityVerifier`), прокси и webhook на каждый коннектор, обязательная изоляция прокси (сеть, `aud` + `--oidc-audience`, Cedar на прокси), Bearer вызывающего доходит до коннектора. Главное — топология: прокси `thv` не стартует без container runtime. Вне Kubernetes это docker socket в каждом прокси (root на хосте), в Kubernetes — кластер, которого в целевой платформе нет. Стоимость перехода — ~12–17 дней + эксплуатация кластера (оператор) или ~9–12 дней с непроверенными мерами против root на хосте (`thv run`), см. п.9. Выигрыш — Cedar вместо `unified_pdp` ContextForge.
- **Docker MCP Gateway** не поддерживает ни multi-tenant, ни identity вызывающего: один общий bearer-токен на инстанс, один `mcp.Server` на все сессии. Политики вне Docker Desktop разрешают всё. Перехватчики не умеют менять запрос. Все релизы помечены pre-release. Вариант C без форка невозможен.

**Что изменилось после цикла 2.** В цикле 1 стоимость ToolHive считалась от худшего пути (Go-стратегия в своей сборке vMCP, ~8–12 дней плюс постоянная пересборка). Путь через mutating webhook не требует своей сборки. После учёта топологии в цикле 3 по дням он не дешевле пути G: (а) ~12–17, (б) ~9–12 против ~8–12. Зато он не требует пересборки vMCP на каждый релиз. Рекомендация не меняется, потому что решает разница 0 против ~12–17 дней (или ~9–12 с root на хосте) и то, что ContextForge уже проверен на всех путях M4, а ToolHive — только на `thv run` с docker socket на стенде. **После цикла 3:** механизм пути C на ToolHive проверен, а продакшн-топология — нет. Поэтому ToolHive — запасной кандидат с проверенным механизмом, но не готовая альтернатива: перед переходом нужно выбрать Kubernetes (и принять его эксплуатацию) или доказать, что `thv run` работает без root-доступа к docker на хосте.

**Когда пересмотреть.** Переход на ToolHive (путь webhook) имеет смысл, если в M5 ContextForge не выполнит условие 4 GO/NO-GO: `unified_pdp`, deny by default на всех путях. Формат JWS и claims не меняются, подписант — тот же Python-код. Меняется канал: `IdentityVerifier` читает JWS из `params._meta["gxg.dev/identity"]`, это правка SEC-03. Перед переходом нужно сначала решить топологию (Kubernetes или `thv run` без root-доступа к docker) и проверить её вживую.

## M5: условие 4

Проверено на dev-стенде M5 (2026-11-21, [stand/README.md](../../stand/README.md), [отчёт](../../reports/conformance/M5.json)). Встроенный плагин `unified_pdp` ContextForge v1.1.1: движок `native`, `default_decision: deny`, `combination_mode: all_must_allow`, кеш решений выключен. Правила — точный email агента × точное имя tool ([`stand/unified_pdp.rules.json`](../../stand/unified_pdp.rules.json)). Плагин стоит перед адаптером identity, поэтому запрещённый вызов не получает и JWS.

- Без правила allow вызов отклоняется (`PDP_DENY`) на `/rpc`, на virtual server (MCP и SSE), по алиасу и на глобальном `/sse`. До коннектора он не доходит (по аудиту `demo`). На SSE ContextForge отвечает на отказ пустым `result: {}` без причины: это не обход, но агент не видит, почему.
- Глобальный `/mcp` отказывает team-scoped токену агента для любого tool (RBAC `tools.execute`), как в M4.
- Deny-правило `tools.invoke.*execute*` срабатывает раньше allow. Проверено ошибочным allow на `demo-message-execute` для `t-alpha:reader`.
- Неизвестный правилам субъект (токен platform admin) отклоняется.
- Если файл правил не читается, `native` остаётся без правил и запрещает всё. Если плагин не загрузился, ContextForge не стартует (`PLUGINS_FAIL_ON_PLUGIN_ERROR=true`).

**Итог: условие 4 выполнено, переход на ToolHive не нужен.** Одна находка: REST-tool, созданный с `visibility` рядом с `team_id`, а не внутри `tool`, становится `public` и виден агентам других team. Вызвать его не даёт `unified_pdp`: deny by default. Bootstrap стенда ставит `visibility` внутри `tool` и чинит существующие записи.

## Стенд и атаки

Оба кандидата прогнаны тем же набором, что M4: `spikes/m4.1-gateways/attacks.py` импортирует `spike.py` (HTTP, MCP-сессия, `tools/call` с аргументами `{"text": "привет", "lang": "ru"}`, поддельный JWS) и `check_verdicts.EXPECTED` из M4, echo-MCP с верификатором варианта C — тот же `echo/` M4. Каждый `tools/call`, дошедший до echo, получает вердикт верификатора при приёме.

- **ToolHive:** один vMCP на оба tenant'а, static backends `alpha` → `/mcp/t-alpha`, `beta` → `/mcp/t-beta`, `hidden` → `/mcp/t-hidden` (tool скрыт фильтром агрегации). Incoming — OIDC от mock IdP, claim `tenant_id`; 4 агента (client_credentials), platform admin = токен с `roles: [admin]` без `tenant_id`. Cedar: `call_tool` на `alpha_echo` только при `principal.claim_tenant_id == "t-alpha"`, на `beta_echo` и `hidden_echo` — при `t-beta` ([`vmcp.yaml`](../../spikes/m4.1-gateways/toolhive/vmcp.yaml)). Варианты: `token_exchange` к обоим коннекторам; STS недоступен; невалидная политика; апгрейд с `v0.66.0`; путь C через webhook (`WEBHOOK=1`, ниже); webhook остановлен со старта и посреди сессии.
- **ToolHive, путь C (`webhook-c`):** vMCP (тот же Cedar) → `token_exchange` → `thv run http://…/mcp/t-alpha` (и `t-beta`) из закреплённого образа `thv`, у каждого OIDC от того же IdP и `--webhook-config` с mutating webhook `failure_policy: fail`, HMAC ToolHive → echo. Webhook — [`webhook.py`](../../spikes/m4.1-gateways/toolhive/webhook.py), ~100 строк Python: claims как у плагина `gxg_identity` (из principal, который прокси получил из `token_exchange`-токена), `ahs` — тем же `canonical()`, что у верификатора. Отказ (403, до коннектора не доходит): чужой tenant для этого коннектора, нет `tenant_id` (admin), email не из домена агентов tenant'а, неизвестный сервер, плохая HMAC. Echo проверяет JWS тем же `verify_jws.verify`, но берёт его из `_meta` (`ECHO_IDENTITY_META`). Дополнительный путь `thv-proxy:direct` — собственный токен агента прямо на прокси, мимо vMCP. Это topology-тест. Kubernetes нет, поэтому `MCPServer` + `MCPWebhookConfig` не поднимались: `thv run` — тот же код прокси (`TH/pkg/runner/middleware.go#L59`), в операторе его же запускает proxyrunner, а vMCP ходит к `MCPServer.Status.URL` (`TH/pkg/vmcp/workloads/k8s.go#L235-L241`).
- **Docker MCP Gateway:** identity вызывающего у шлюза нет, поэтому tenant = инстанс: `gw-alpha` (echo-alpha + echo-hidden, `--tools=echo-alpha:echo`), `gw-beta`, и `gw-shared` — один инстанс на двоих, чтобы показать, что он даёт двум tenant'ам. Транспорт `streaming`, токен `MCP_GATEWAY_AUTH_TOKEN` на инстанс (оба агента tenant'а держат один и тот же), `--static`: без него шлюз в контейнере ходит в Docker API и падает при старте (`guessing network: Cannot connect to the Docker daemon`). Admin-роли у шлюза нет.

### 1. Изоляция tenant'ов

- **ToolHive — passed, со своей моделью tenant'ов.** Tenant, team или org в коде нет. Группа (`groupRef`) — один набор backend'ов на инстанс vMCP. Разным клиентам разное видно только через Cedar: admission фильтрует списки и отклоняет вызовы по identity (`TH/pkg/vmcp/core/admission.go`, `FilterTools`, `AllowToolCall`). На стенде один vMCP на двоих: `tools/list` агентов t-alpha → `["alpha_echo"]`, t-beta → `["beta_echo"]`, admin → `[]` ([`evidence/default/visibility.json`](../../spikes/m4.1-gateways/toolhive/evidence/default/visibility.json)). Вызов `beta_echo` агентом t-alpha → 403. Изоляция держится на политике, которую генерируем мы: ошибка в политике = утечка между tenant'ами. Политика ссылается на имя tool после префикса (`alpha_echo`), поэтому смена `prefixFormat` молча ломает её в сторону отказа, не разрешения.
- **Docker MCP Gateway — failed.** Один `mcp.Server` на все HTTP-сессии: `NewStreamableHTTPHandler(func(_ *http.Request) *mcp.Server { return g.mcpServer })` (`DG/pkg/gateway/transport.go#L59-L61`). Аутентификация — один общий токен (`DG/pkg/gateway/auth.go#L34-L47`). На общем инстансе агент t-alpha вызвал `beta__echo` и дошёл до коннектора t-beta. С инстансом на tenant изоляция есть (чужой токен → 401), но агентов внутри tenant'а различить нельзя. Кроме того, dynamic tools включены по умолчанию, и `mcp-add` меняет общий `serverNames` для всех клиентов (`DG/pkg/gateway/mcpadd.go#L81-L85`). На стенде они выключены флагом `--servers`.

### 2. Проверяемая identity к коннектору и путь к варианту C

- **ToolHive, встроенное.** Подписанного identity-заголовка или identity в `_meta` нет. Стратегии outgoing auth vMCP: `unauthenticated`, `header_injection` (статичное значение или env), `token_exchange`, `upstream_inject`, `aws_sts`, `obo` (заглушка «enterprise required», `TH/pkg/vmcp/auth/obo.go#L17-L22`), `xaa` (`TH/pkg/vmcp/auth/types/types.go#L26-L59`).
- **ToolHive, `token_exchange` вживую.** Коннектор получает `Authorization: Bearer` — JWT, подписанный IdP, с `sub`, `email`, `tenant_id`, `jti`, `exp`. Все 5 вызовов через шлюз проходят проверку по JWKS IdP. Кеша нет: exchange выполняется на каждый запрос к backend (`TH/pkg/vmcp/auth/strategies/tokenexchange.go#L137-L146`; пакет `pkg/vmcp/cache` в `v0.67.0` не импортируется). Поэтому `jti` уникален на вызов: у `hermes@t-alpha` 2 вызова — 2 разных токена, `jti_reused_across_gateway_calls: false`. Результат по критериям ADR-0001 ([`verify_tx.json`](../../spikes/m4.1-gateways/toolhive/evidence/token-exchange/verify_tx.json)):
  - Критерий 1: `tenant_id` и `sub` агент не подделает, их подписывает IdP. Но `_meta` и аргументы агента проходят рядом.
  - Критерии 2–3 (повтор): по подписи и `exp` перехваченный токен проходит и сразу, и через 65 с (`direct_replays_still_valid`), но срок 3600 с задал стенд (`oidc.json` `tokenExpiry`), а не ToolHive. Хранилище `jti` коннектора (SEC-03: одно на коннектор, общее для его реплик; в `verify_tx.py` — по ключу `(path, jti)`) отклоняет 4 из 5 прямых повторов: сразу, с подменой аргументов, на другой tool, через 65 с. Повтор на **другой** коннектор хранилище не видит (`direct_replays_rejected_by_jti_store.replay_other_connector: false`), его закрывает только `aud`. Значит, повтор на тот же коннектор закрывается хранилищем `jti` плюс коротким `exp` у IdP (≤ 60 с), на другой — только `aud`.
  - Не закрывается привязка к вызову: в токене нет `tool` и `ahs`. Перехватчик между шлюзом и коннектором может подменить аргументы или tool **до** легитимного вызова, и коннектор примет. Это и есть провал по SEC-03.
  - Повтор на другой коннектор проходит и подпись, и хранилище: mock IdP не ставит `aud` при exchange, хотя vMCP передаёт `audience` (`TH/pkg/vmcp/auth/strategies/tokenexchange.go#L311`). Это свойство mock IdP, а не ToolHive: с IdP, который ставит `aud`, этот повтор отклонялся бы.
- **ToolHive, вариант C — два пути без форка.**
  - **Путь W: mutating webhook прокси за vMCP — passed на стенде.** У `thv run` и proxyrunner есть middleware `mutating` (`TH/pkg/runner/middleware.go#L59`). В операторе это `MCPServer.spec.webhookConfigRef` → `MCPWebhookConfig` (`TH/cmd/thv-operator/api/v1beta1/mcpserver_types.go#L355-L358`, `failurePolicy` по умолчанию `fail`). Webhook получает `principal` (без токена) и `mcp_request` (`TH/pkg/webhook/types.go#L191-L204`) и возвращает JSON Patch. Патч ограничен `/mcp_request/…` (`TH/pkg/webhook/mutating/patch.go#L61-L66`), поэтому JWS кладётся в `params._meta["gxg.dev/identity"]`, а не в заголовок. Запрос подписан HMAC (`X-ToolHive-Signature`, `TH/pkg/webhook/signing.go`), webhook её проверяет. Явный отказ webhook соблюдается при любой `failure_policy`. Ошибка webhook при `fail` → 500 `Webhook error` (`TH/pkg/webhook/mutating/middleware.go`).
    - Вживую ([`webhook-c/`](../../spikes/m4.1-gateways/toolhive/evidence/webhook-c/summary.json)): 8 вызовов агентов (4 через vMCP, 4 прямо на прокси) приняты верификатором M4 с identity вызвавшего агента и `tool = echo`. Прямые атаки на коннектор: `missing X-GxG-Identity`, `replayed jti`, `arguments hash mismatch`, `InvalidAudienceError`, `bad tool`, `InvalidSignatureError`, `ExpiredSignatureError` — ровно `check_verdicts.EXPECTED`. Admin и чужой tenant прямо на прокси — 403 от webhook ([`webhook.log`](../../spikes/m4.1-gateways/toolhive/evidence/webhook-c/webhook.log)).
    - Что мы при этом теряем. (1) JWS в `_meta`: SEC-03 и `IdentityVerifier` кита нужно перевести на этот канал, коннектор должен убирать ключ из `_meta` до бизнес-логики. (2) Прокси пропускает к коннектору заголовки клиента: поддельные `X-Forwarded-User-*` и `X-GxG-Identity` дошли до echo (`thv-proxy:direct`, `attack_forge`). Это безопасно, только пока коннектор берёт identity исключительно из JWS. Пропускается и `Authorization` вызывающего (сырой лог echo `webhook-c`): на прямом пути коннектор получает собственный токен агента (`aud: vmcp`, 3600 с), через vMCP — exchange-токен (без `aud`, 3600 с). Скомпрометированный коннектор с токеном агента вызовет через vMCP любой tool, разрешённый этому агенту, в том числе на других коннекторах tenant'а. С exchange-токеном он вызовет свой прокси, и webhook подпишет ему свежий JWS от имени агента. В ContextForge + C коннектор токен агента не получает. Меры: IdP ставит `aud` = прокси при exchange плюс `--oidc-audience` на каждом прокси (токен агента `aud: vmcp` прокси отклонит, exchange-токен годен только для своего прокси); сеть, где коннектор не видит vMCP и чужие прокси; strip-auth. Strip-auth в `v0.67.0` включается только с embedded auth server (`TH/pkg/runner/middleware.go#L495-L527`, `disableUpstreamTokenInjection` или token-only), а с `--oidc-issuer` — нет. Embedded auth server сам выпускает токены вместо внешнего IdP, совместимость с `token_exchange` vMCP не проверяли. (3) Агент со своим токеном IdP может обратиться к прокси напрямую мимо vMCP: подпись будет верной, tenant проверит webhook, но правила Cedar vMCP по tool не применятся — вживую вызывались и скрытые tools того же коннектора. Меры, любая или вместе: сеть, где до прокси ходит только vMCP (NetworkPolicy); IdP, который ставит `aud` при exchange, плюс `--oidc-audience` на прокси (на mock IdP не проверить); Cedar на самом прокси — `thv run --authz-config` (`TH/cmd/thv/app/run_flags.go#L237`). Его middleware стоит после mutating webhook и до backend (`TH/pkg/runner/middleware.go#L202-L242`), поэтому закрывает и скрытые tools на прокси. Это самое дешёвое средство, но политики приходится генерировать дважды: для vMCP и для каждого прокси. Вживую не проверяли. (4) Лишний сетевой hop и HTTP-вызов webhook на каждый `tools/call` (не измеряли). (5) API webhook — `v0.1.0` (`TH/pkg/webhook/types.go#L19`), молодой контракт pre-1.0 проекта. Сам webhook-middleware уже обходили: [GHSA-g7gq-2r4g-3qw8](https://github.com/stacklok/toolhive/security/advisories/GHSA-g7gq-2r4g-3qw8) (High, 2026-10-07: POST с не-JSON `Content-Type` обходит webhooks и rate limit) и [GHSA-wj8g-gmv2-mpmv](https://github.com/stacklok/toolhive/security/advisories/GHSA-wj8g-gmv2-mpmv) (2026-11-04: BOM в начале тела — fail-open webhooks пропускают запрос). Оба опубликованы до `v0.67.0`. Для пути W обход webhook означает запрос к коннектору без JWS, и отклонит его только коннектор (`missing`). Поэтому **JWS на коннекторе обязателен для всех методов**, не только для `tools/call`: безопасность пути W держится на коннекторе, а не на webhook. (6) Топология: см. п.9. Прокси не стартует без container runtime: вне Kubernetes — docker socket в каждом прокси, в Kubernetes — оператор и кластер.
  - **Путь G: своя стратегия outgoing auth в vMCP — not_run.** Список middleware прокси — фиксированная map (`TH/pkg/runner/middleware.go#L38-L45`), неизвестный тип → `unsupported middleware type` (`TH/pkg/runner/runner.go#L411-L424`). Точка расширения vMCP — `Strategy.Authenticate(ctx, *http.Request, …)`: вызывается на каждом запросе к backend, в контексте есть identity, в теле — `tools/call`. Подставить можно через `auth.RegisterOBOStrategy` из `init()` внешнего пакета (`TH/pkg/vmcp/auth/obo.go#L51-L55`) или встроив vMCP как библиотеку. Форк не нужен, но нужна своя сборка бинарника и образа. Плюс — JWS в заголовке `X-GxG-Identity`, SEC-03 не меняется, лишнего hop нет. Адаптер под этот путь мы не писали.
  - В самом `pkg/vmcp` webhooks не подключены (grep: только комментарий о Kubernetes admission webhooks в `config/composite_validation.go`). Поэтому путь W работает только с прокси на каждый коннектор за vMCP, а не внутри vMCP.
- **Docker MCP Gateway — failed.**
  - Identity вызывающего нет: единственное, что шлюз знает о клиенте, — `clientInfo.name` из `initialize`, его выбирает сам клиент.
  - К remote-серверу уходят статичные `remote.headers` из каталога или OAuth-токен самого шлюза. Заголовки клиента не передаются, `_meta` клиента передаётся как есть: `Meta: req.Params.Meta` (`DG/pkg/gateway/handlers.go#L52-L56`).
  - Перехватчики (`--interceptor before|after:exec|docker|http`) не меняют запрос. Непустой вывод `before` подменяет **результат** вместо вызова backend (`DG/pkg/interceptors/interceptors.go#L109-L116`). Вживую на stdio: перехватчик получил `{"Session":{},"Params":{"_meta":{…},"name":"alpha__echo","arguments":{…}},"Extra":null}`, а его вывод вернулся клиенту вместо вызова ([`evidence/interceptors/`](../../spikes/m4.1-gateways/docker-mcp-gateway/evidence/interceptors/)).

  - Вариант C возможен только форком (middleware, который меняет `_meta` или заголовок) плюс собственная аутентификация, иначе подписывать нечего.

### 5. Пути вызова

- **ToolHive.** Агрегированный путь с префиксом `{workload}_` проверен вживую с identity (`token_exchange`) и Cedar. Прокси одного сервера (`thv run`) проверен вживую в варианте пути W: `thv run` для remote URL всё равно требует container runtime (без docker socket не стартует даже `--help`), на стенде он получил socket. Это root на хосте для процесса, который принимает трафик (см. п.9, топология). Заголовки клиента доходят до backend, как и выведено по коду в цикле 1: поддельные `X-Forwarded-User-*`, `X-Tenant-Id`, `X-GxG-Identity` дошли до echo. Identity при этом верная, потому что echo берёт её только из JWS в `_meta`. До коннектора доходит и `Authorization` вызывающего (см. п.2 (2)). Прямой путь к прокси мимо vMCP обходит Cedar vMCP (см. п.2 (3)), меры — сеть, `aud` + `--oidc-audience`, `--authz-config` на прокси. Overrides (переименование tool) — **not_run**.
- **Docker MCP Gateway — failed.** Identity нет ни на одном пути. `mcp-exec` и code-mode вызывают handler напрямую, перехватчики видят только внешний вызов (`DG/pkg/gateway/mcpexec.go`, `codemode.go`). Для prompts и resources перехватчиков нет.

### 7–8. Зрелость и эксплуатация

- **ToolHive.** Apache-2.0; `SECURITY.md`: GHSA или security@stacklok.com. Образы подписаны (`.github/workflows/image-build-and-publish.yml`). Среди 55 GHSA два — обходы webhook-middleware, на котором стоит путь W (GHSA-g7gq-2r4g-3qw8, GHSA-wj8g-gmv2-mpmv, п.2 (5)), поэтому JWS проверяется на коннекторе для всех методов. Хранилище — файлы RunConfig, CRD/ConfigMap в Kubernetes, Redis для сессий vMCP. PostgreSQL нет. Аудит: JSON-события с `subjects.user` проверены вживую (`evidence/default/vmcp.log`, `"level":"AUDIT"`). OTel-трейсы и метрики, Prometheus `/metrics` на 9464 (по конфигу, не запускались).

Телеметрия — через Docker CLI. Шлюз рассчитан на Docker Desktop: без него приходится ставить `DOCKER_MCP_ALLOW_INSECURE_REMOTE_URLS=1` (снимает все SSRF-проверки для всех remote-серверов) и `--static`.

## Что не проверено

- ToolHive, топология пути W: (а) оператор (`MCPServer` + `MCPWebhookConfig`, proxyrunner, NetworkPolicy) и стоимость кластера — нет кластера; (б) `thv run` без root-доступа к docker на хосте (rootless Podman, socket-proxy с урезанным API, отдельная VM) — не пробовали; проверен только `thv run` с полным docker socket.

- ToolHive, прочее: путь G вживую (адаптер не писали); задержка webhook; апгрейд пути W; overrides; Redis-сессии.
- Docker MCP Gateway: перехватчики на `sse`, HTTP-перехватчик со статусом 500, профили (feature flag), режим с docker socket.
