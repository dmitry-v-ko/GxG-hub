# ADR-0006: KB-сервис — отдельный сервис и MCP-сервер по MCC за ContextForge

**Статус:** Accepted — решение владельца, 2026-11-22.

## Решение

`dmitry-v-ko/gxg-kb-service` — отдельный сервис. Он единственный вход в Knowledge Base, данные которой лежат в Supabase. Сервис сам является MCP-сервером по [MCC](../specs/mcp-connector-contract-v1.md) за ContextForge и строится на шаблоне MCP Toolkit (M1.1). Кода прежнего MCP-сервера KB (`kb.agents.gxg-labs.com/mcp`) нет в доступных репозиториях, и 2026-11-22 сервер отвечал 502. Поэтому сервис пишется с нуля, а контракт и выводы берутся из `docs/audits/kb-gap-audit.md`.

## Доступ

- **Что:** видимость tools — через RBAC и `unified_pdp` ContextForge | **Зачем:** агент видит только свои tools | **Почему:** иначе агент вызывает tools, на которые у него нет прав.
- **Что:** коллекции — через grants: RID `kb:<connection>/collection/<entity_type.key>`, `not_found` побайтно для чужих документов | **Зачем:** изоляция коллекций и tenant'ов (GR, SC-05) | **Почему:** в самой KB понятия коллекции нет (G5 аудита).
- **Что:** сервис читает Supabase отдельной ролью Postgres только на `SELECT` в схеме `kb` | **Зачем:** «только чтение» гарантирует база (AC-M6-04) | **Почему:** общие ключи KB по ролям (G3/G4) не дают агентной изоляции и берут самый сильный ключ.
- **Что:** запись в KB (`write_reversible`) — позже, отдельной ролью и через `propose` | **Зачем:** у записи есть согласование | **Почему:** в M6 записи нет.
- **Что:** Mastra из `gxg_agents_v2` ходит в KB через Hub, а не через свой клиент | **Зачем:** один вход, одни права, один аудит | **Почему:** иначе остаётся обход мимо политики.
