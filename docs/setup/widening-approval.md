# Подтверждение расширения прав: метка `widening-approved` (AC-M2-04)

**Зачем.** GR-10 требует, чтобы PR, расширяющий права, одобрил человек, который не автор. Мейнтейнер один, поэтому по решению владельца ревью второго человека заменено явным подтверждением владельца — меткой `widening-approved` на PR.

## Как работает проверка

Job `grants-widening` в `.github/workflows/ci.yml` входит в `ci-ok`, а `ci-ok` уже обязателен для `main` ([branch-protection.md](branch-protection.md)). Отдельно добавлять проверку в ruleset не нужно.

На каждом событии PR (`opened`, `synchronize`, `reopened`, `labeled`, `unlabeled`) job:

1. Строит отчёт `gxg-policy diff <base>/policies policies` и публикует его комментарием в PR. Комментарий один, он обновляется.
2. Если в отчёте нет `widening`, проверка зелёная.
3. Если `widening` есть, проверка зелёная только при трёх условиях:
   - на PR висит метка `widening-approved`;
   - метку поставил пользователь из `.github/CODEOWNERS`. Файл берётся из **базового** коммита PR, поэтому PR не может вписать туда своего автора;
   - метку поставили руками. Если событие выполнено через GitHub App (`performed_via_github_app`), например агентом от имени владельца, оно не засчитывается.
4. Если в PR пришёл новый push и в отчёте есть `widening`, job снимает метку, и проверка краснеет. Подтверждение относится к тому, что владелец видел, а не к будущим коммитам.

Что считается расширением, решает `gxg-policy diff`:

- новые пары (subject, action, resource), включая появившиеся через группы;
- продлённый `expires_at`;
- новые роли людей;
- новые и ослабленные `auto_approve`, удалённые или ослабленные `require_approval` и `deny`;
- выросшие сроки и квоты;
- новые сервисы, tenant'ы сервисов и webhooks в реестре платформы.

Изменённый `match` у правила считается расширением всегда: так безопаснее.

## Что делает владелец

1. Открыть PR и прочитать комментарий «Policy diff (gxg-policy)», раздел **Widening**.
2. Если расширение нужно, поставить метку: **Labels → `widening-approved`** в правой колонке PR, или командой `gh pr edit <номер> --add-label widening-approved`.
3. Метку должен поставить сам владелец со своего аккаунта, а не агент через Claude GitHub App: такое событие проверка отклонит.
4. После каждого нового push с расширением метку нужно поставить заново: job снимает её сам.

Если метки ещё нет в репозитории: **Issues → Labels → New label**, имя `widening-approved`.

## Кто может ставить метку и почему засчитывается только владелец

**Ограничить, кто ставит метку, GitHub не позволяет.** Метки на PR может ставить любой, у кого есть роль Triage или выше. В репозитории на личном аккаунте это любой коллаборатор: отдельных прав на конкретную метку нет.

Поэтому защиту обеспечивает сама проверка, а не права на метку. Метку может поставить кто угодно, но засчитывается она, только если поставил пользователь из CODEOWNERS базового коммита. Сейчас там один пользователь — `@dmitry-v-ko`. Команды (`@org/team`) не учитываются.

## Ограничения

- **Workflow можно изменить в том же PR.** Workflow `pull_request` запускается из ветки PR. PR, который правит `.github/workflows/ci.yml` или `scripts/ci/widening_gate.py`, может отключить проверку для себя. Эти файлы закреплены за владельцем в CODEOWNERS, но обязательного ревью нет (решение по AC-M0-03). Надёжно закрыть этот путь можно двумя способами: обязательным ревью code owner'а при втором человеке или required workflow через ruleset организации. `pull_request_target` проблему не решает: по документации GitHub его проверки не всегда засчитываются как required.
- **Токен владельца у агента.** Если агент действует личным токеном владельца, а не через GitHub App, событие метки неотличимо от ручного. Агентам нельзя выдавать личные токены владельца.
- **Точность diff зависит от «up to date».** Отчёт сравнивает вершину базовой ветки с head PR. Это точно, пока в ruleset включено *Require branches to be up to date before merging* ([branch-protection.md](branch-protection.md)).
- **PR из форков** получают токен только на чтение. Комментарий не публикуется, проверка пишет предупреждение. Решение принимается так же, а снять метку при новом push job не сможет и упадёт: fail closed.
- **Первый PR с этой проверкой.** Метки `widening-approved` нет, пока её не создадут. Если в базовой ветке нет `policies/`, все политики в PR считаются `widening`.
