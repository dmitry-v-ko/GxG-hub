# Первый эксперимент (не миграция)

Цель: доказать, что ContextForge подходит как ядро вместо самостоятельной инфраструктуры Hub.

## Этапы

1. Запустить ContextForge локально; проверить работу Admin UI и авторизованного MCP клиента.
2. Подключить тестовый knowledge MCP read-only (существующий сервис, без копирования базы).
3. Зарегистрировать двух отдельных агентов / машинных клиентов и убедиться в раздельных правах.
4. Добавить тестовый Telegram MCP read-only с ограничениями по chat ID.
5. Создать второй tenant; доказать, что нельзя увидеть или вызвать capabilities, Connections и данные соседнего tenant.
6. Внутри Telegram MCP реализовать две **тестовые** реализации `telegram.search` и проверить deterministic technical fallback при подтверждённом transport error.
7. Проверить denial при прямом вызове неразрешённого инструмента, при подмене agent ID, chat ID и tenant.
8. Убедиться, что audit связывает вызов с agent principal, tenant, инструментом и результатом, не сохраняя содержимое личных сообщений.

## Дальнейший PoC: approval для эффектов (отдельная фаза)

9. Создать тестовый Approval Service/Inbox и тестовое действие с эффектом, которое **не исполняется** до решения проверенного человека.
10. Доказать, что одобрение другого tenant, другой цели/содержимого, просроченное или повторно использованное не открывает выполнение; прямой вызов коннектора тоже не обходит проверку.
11. Доказать корреляцию `approval_request_id`, `invocation_id`, `business_task_id`; повтор после неясного исхода не дублирует эффект.

## Критерии приёмки

- [ ] Список инструментов по двум agent principals отличается согласно политике.
- [ ] Прямой вызов запрещённого инструмента отвергается на сервере.
- [ ] Доступ к чужому tenant/chat/knowledge scope отвергается.
- [ ] Проверка политики не полагается на произвольные поля, переданные агентом.
- [ ] Допустимый технический fallback работает без утечки данных или повышения прав.
- [ ] Нет повторной отправки или другого effect при неопределённом исходе.
- [ ] Существующие KB, Signals и Voice работают без изменений.
- [ ] После рестарта тестовые политики и соединения восстановимы.
- [ ] Контрактные тесты для reference MCP и KB проверяют input/output, identity, resource scopes и стабильную классификацию ошибок.
- [ ] При требуемом человеческом подтверждении никакого side effect нет до валидного согласования (в отдельной фазе effects PoC).
- [ ] Изменение получателя/содержимого и повторная попытка с устаревшим approval не проходят (effects PoC).

**Go/no-go:** если ContextForge не позволяет безопасно реализовать передачу идентичности, политики ресурсов или изоляцию tenant без правки upstream, вернуться к сравнению с agentgateway и минимальным custom control-plane. Ничего не мигрировать до успешного теста.

Никакие пункты выше пока не выполнены: это план проверки.
